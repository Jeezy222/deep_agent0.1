## 目标范围
- 全面静态/动态检查 apps/server 与 apps/web 的所有代码，定位语法、逻辑、运行时与性能问题。
- 在不改变既有功能与模式前提下，迭代修复，并确保风格一致、测试全部通过。

## 基线与环境
- 不改动 .env 内容；仅在本地读取环境变量，避免提交敏感信息。
- 关闭现有重复/残留开发服务器，统一重启：后端 FastAPI (8001)、前端 Vite dev server。
- 使用现有工具链：TypeScript + ESLint + Vite；Python + FastAPI + SQLAlchemy + Pydantic + Uvicorn；已有 tests。

## 静态检查（语法/类型/风格）
- 前端：
  1. 运行 `tsc --noEmit` 做类型检查。
  2. 运行 ESLint 全量扫描并按规则最小化自动修复；人工审查无法自动修复项。
  3. 聚焦 src/services、pages、components 的导入/类型定义一致性（如可选字段、null 处理）。
- 后端：
  1. 运行 `python -m pyflakes` 或 `flake8`（若已配置）进行语法与常见错误扫描。
  2. 运行 `isort`/`black --check`（若已配置）保持风格一致；仅在项目已有规范基础上格式化。
  3. 可选运行 `mypy`（若项目已有类型注解约束）针对关键模块（controllers、services、schemas）。

## 逻辑审查（代码路径/边界条件）
- 支付与订阅：
  - 检查 `payment_controller.py` 的下单、网关中转、回调验签流程是否一致（签名字段、状态迁移）。
  - 校验订单状态机（PENDING/PROCESSING/PAID/FAILED）与订阅更新一致性；避免重复入账与幂等问题。
- 组织租户与用量：
  - 检查 `OrganizationService` 的增删改查、分页与统计；确认空数据/404 的恢复路径与 UI 提示。
- 前端路由与数据：
  - 校验 `api.ts` 接口返回类型与后端 `schemas.py` 的一致性；
  - 审查页面空值保护（如日期/计划名）与列表渲染键值稳定性。

## 性能与稳定性检查
- 后端：
  - 关注潜在 N+1 查询、长耗时同步操作（如网络 IO）；必要时将密集逻辑放入后台任务。

- 前端：
